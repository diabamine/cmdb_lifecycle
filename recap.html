Project recap

CMDB Lifecycle Matcher

Take dirty CMDB rows (vendor, product, version), match each one to a canonical product, and attach end-of-life dates and known vulnerabilities. Everything runs offline against a snapshot you fetch once.

How the mock CMDB is built

No public dataset of a real enterprise CMDB exists, and production data cannot leave your environment. So there are two stand-ins, each answering a different question.

syntheticGenerated, with an answer key

Answers “is the matcher right?” because every row has a known truth. make_synthetic_cmdb.py

  1. Pick a real product from the endoflife.date catalogue, weighted so a few popular products dominate (Pareto), and a real release of it.
  2. Write the clean values: vendor from its CPE id, version from the release.
  3. Inject noise: typos, upper/lower case, reversed words, edition suffixes, vendor aliases, missing vendors, odd version formats, package-style strings.
  4. Add 10% hardware models and 7% in-house apps that must stay unmatched.
  5. Write cmdb_synthetic.csv (5,000 rows) and a separate cmdb_truth.csv.

real dataPublic software catalogues, untouched

Answers “what does real-world naming look like?” There is no answer key. fetch_inventory.py

  1. winget: 15,979 Windows apps, with publisher, display name, latest version.
  2. Homebrew casks: 7,814 macOS apps, with no vendor at all.
  3. Ubuntu 22.04 packages: 6,090 apt packages, with maintainer and epoch-style versions.
  4. No noise is added. These are 29,997 rows as published, and this is what the app analyses.

How matching works, step by step

A row goes through a cascade from cheap and certain to expensive and doubtful. It stops at the first confident answer. Each row keeps the method, a confidence score and a reason if it needs a human.

Lifecycle status, by example

RHEL 9, dates from the Red Hat API, compared with 6 Nov 2026.

Full support ends 2027-05-31, maintenance 2032-05-31, the paid ELS add-on 2036-05-31. Only the first interval is free of risk.

What the matcher refuses to do. It never invents a date. If the product matches but the version does not, the row keeps the product and gets a review reason. In-house applications are expected to stay unmatched, and rows with no vendor are only matched on long, unambiguous names.

How to improve it

Separate two kinds of miss before fixing anything. “No lifecycle exists for this product” cannot be solved by better matching. “The product exists but the name did not match” can.

shippedSub-package rollup

95 rows now match through it: libssl3 → OpenSSL, postgresql-doc-14 → PostgreSQL, libpython3.10-minimal → Python.

  • Strips Debian and RPM suffixes (-dev, -doc, -utils), version tokens and library soname digits.
  • A short explicit list covers gcc, glibc, the Linux kernel, OpenSSL, PostgreSQL and a few more.
  • Language bindings are guarded: python3-debian can never become Debian.

shippedVendor-aware name rules

173 rows match through vendor rules and 138 more through cleaning: Mozilla Firefox (hu), Firefox Developer Edition (ach), .NET runtimes, Visual Studio BuildTools 2019, Java(TM) SE Development Kit 23.

  • Removes locale codes, edition words and the vendor's own name from the product.
  • Rules for .NET, Visual Studio, Java SE and Firefox or Thunderbird.
  • Guessed spellings are used for exact lookup only, never for fuzzy search.

shippedAlias table and review loop

The new Review queue tab lists unsure rows grouped by spelling, biggest first.

  • Three actions: accept the suggestion, map to another product, or mark as not a catalogue product.
  • Each decision is saved to aliases.csv and wins over every rule.
  • Only the affected rows are re-matched. Tested: one “not a product” decision changed one row, a mapping gave method alias with confidence 100, and all other rows stayed identical.

side effect132 earlier matches were dropped

A stricter rule for short names and an 85 floor after penalties removed fuzzy matches that were wrong, such as Scalar → Scala, Akiflow → Apache Airflow and Steam → CentOS Stream.

I checked 30 of the 132. All 30 were wrong or doubtful, so the matched count rose by a net 266 while precision improved.

One rule for all AI use. AI maps names and extracts text. It never supplies a date or a CVE from memory. Dates come from the snapshot, with provenance, and a model’s output is a candidate that passes the same thresholds as any other.

Taking it to a real CMDB and new sources

The engine already works on any CSV with vendor, product and version. What changes in the real world is the data around it: how you feed it, how you measure it, and how you add sources.

step 1Map your export

Rename columns to vendor, product, version, ci_type, fw_or_pkg and add an asset id. Hardware rows get ci_type = hardware. Nothing else is required.

step 2Run it where the data lives

Only the snapshot travels in. The CMDB never leaves your network, which matches your security constraint. Refresh the snapshot monthly with run_all.sh on a connected machine.

step 3Label a small sample

Hand-check 200 to 300 rows, weighted toward production and critical assets. Compute precision and recall at the thresholds, then tune AUTO and REVIEW on that.

step 4Work the review queue

Use the Review queue tab: each decision is saved to aliases.csv and applies before any rule. Expect the first pass to be heavy and each later one lighter.

step 5Write back and monitor

Push lifecycle status, EOL date, CVE counts and the match confidence into the CMDB. Track auto-accept rate, sampled precision, queue size and snapshot age on the coverage tab.

step 6Keep provenance

Store the source, URL and fetch date of every date you display. When a vendor moves an end-of-support date, you can show where the old one came from.

Open risks to plan for

  • Scrapers break when a page layout changes, so check record counts after every run and review each site’s terms.
  • NVD entries without version bounds count as “all versions”, which overstates old CVEs.
  • Name-only NVD matches are low trust and should be verified.
  • The Cisco collector has never run against the live API.
